# ARIS Fitness Routine App — Technical Specification
**Platform:** Android (native)
**Target Implementer:** AntiGravity (AI coding agent)
**Document Type:** Enterprise-grade architecture & implementation handoff
**Version:** 1.0

---

## 1. Purpose

A daily-routine and diet-tracking Android app built around **5 selectable "Character Profiles."**
Each character has a pre-defined **3-year (1,095-day) day-indexed routine** covering:
- Wake/sleep schedule
- Meal schedule with calorie/macro targets
- Workout schedule

The app personalizes the character's reference routine to the actual user via their height/weight
(and optionally age, gender, activity level), then drives the user's day through **scheduled
alarms and notifications** for wake time, meals, calorie targets, and workouts.

This is **not** a generic habit tracker — it is a **data-driven routine engine**. The 3-year
routine content itself (per character) is supplied by Aris as structured data (see Section 5)
and imported into the app; it is not generated by the app.

---

## 2. Core User Flow

1. **First Launch — Onboarding**
   - Collect: height (cm), weight (kg), age, gender, activity level (sedentary → very active)
   - Calculate BMR (Mifflin-St Jeor) → TDEE
   - Present the 5 characters (name, short description, difficulty/intensity tag)
   - User selects one character → `start_date = today`, `day_index = 1`

2. **Daily Operation**
   - App resolves `day_index` from `start_date` + elapsed calendar days (handles app being closed/reopened)
   - Pulls that day's `DailyRoutineEntry` for the selected character
   - Scales meal calorie targets to the user's TDEE (see Section 4.3)
   - Schedules today's alarms/notifications (wake, meals, workouts, reminders)
   - Home screen shows: today's checklist, current streak, calories consumed vs. target

3. **Ongoing**
   - User can log actual meals/workouts as done (checkbox or manual calorie entry)
   - Missed-day handling: routine does **not** silently skip — see Section 6.4 (pause/resume logic)
   - Progress view: day X of 1095, adherence %, weight trend (optional manual weight log)

## 3. Data Model

### 3.1 User Profile
```json
{
  "user_id": "uuid",
  "height_cm": 175,
  "weight_kg": 70,
  "age": 24,
  "gender": "male | female | other",
  "activity_level": "sedentary | light | moderate | active | very_active",
  "bmr": 1680,
  "tdee": 2350,
  "selected_character_id": "char_01",
  "start_date": "2026-09-17",
  "current_day_index": 1,
  "paused_days": []
}
```

### 3.2 Character
```json
{
  "character_id": "char_01",
  "name": "string",
  "description": "string",
  "intensity_tag": "beginner | intermediate | advanced",
  "reference_tdee": 2500,
  "total_days": 1095
}
```
`reference_tdee` = the calorie baseline the routine's meal data was originally designed around.
This is required to compute the scale factor in 4.3.

### 3.3 Daily Routine Entry (the core content unit)
```json
{
  "character_id": "char_01",
  "day_index": 1,
  "wake_time": "05:30",
  "sleep_time": "22:00",
  "meals": [
    {
      "meal_id": "breakfast",
      "time": "06:30",
      "name": "string",
      "base_calories": 500,
      "macros": { "protein_g": 30, "carbs_g": 60, "fat_g": 15 }
    }
  ],
  "workouts": [
    {
      "time": "07:00",
      "title": "string",
      "duration_min": 45,
      "notes": "string"
    }
  ],
  "reminders": [
    { "time": "21:30", "message": "string" }
  ]
}
```
This structure repeats for `day_index` 1 → 1095, per character. **5 characters × 1095 days**
is the full dataset — supplied as JSON/CSV import files, not hand-coded.

## 4. Calorie Personalization Engine

### 4.1 BMR (Mifflin-St Jeor)
```
Male:   BMR = 10*weight_kg + 6.25*height_cm - 5*age + 5
Female: BMR = 10*weight_kg + 6.25*height_cm - 5*age - 161
```

### 4.2 TDEE
```
TDEE = BMR * activity_multiplier
  sedentary   = 1.2
  light       = 1.375
  moderate    = 1.55
  active      = 1.725
  very_active = 1.9
```

### 4.3 Scaling a character's meal calories to the user
```
scale_factor = user_tdee / character.reference_tdee
adjusted_meal_calories = meal.base_calories * scale_factor
```
Macros scale proportionally with calories unless a per-character override rule is defined later.
Workout duration/intensity is **not** auto-scaled — only diet is; exercise scaling (if wanted)
should be a Phase 2 decision, not MVP.

## 5. Content Import Format (for the 5×1095 routine data)

Recommend one CSV per character with columns:
```
day_index, wake_time, sleep_time, meal_time, meal_name, base_calories, protein_g, carbs_g, fat_g, workout_time, workout_title, workout_duration_min, workout_notes, reminder_time, reminder_message
```
Import pipeline: CSV → parsed into `DailyRoutineEntry` rows → inserted into local Room DB at
first app setup (bundled as assets) or via an admin-only import screen if content will be updated
post-release.

## 6. Notification & Alarm Architecture

### 6.1 Why native Kotlin (not Flutter/React Native)
Exact-time alarms (wake time, meal time) that must fire reliably even when the app is killed or
the device is in Doze mode require direct control over `AlarmManager.setExactAndAllowWhileIdle()`
and battery-optimization exemptions. Cross-platform frameworks add an extra layer that frequently
breaks this reliability on OEM Android skins (Xiaomi, Samsung, etc.). **Recommendation: native
Kotlin + Jetpack Compose.**

### 6.2 Components
- `AlarmManager` — exact wake/meal/workout time triggers
- `WorkManager` — daily rescheduling job (runs once after midnight to queue next day's alarms)
- `BroadcastReceiver` — handles fired alarms → posts notification
- `NotificationChannel`s — separate channels: Wake, Meals, Workouts, General Reminders (user can
  mute/customize per category — Android requirement, also good UX)

### 6.3 Required permissions / OS considerations
- `SCHEDULE_EXACT_ALARM` (Android 12+) — must request and handle denial gracefully
- Battery optimization exemption prompt (guide user to disable for reliability)
- `POST_NOTIFICATIONS` runtime permission (Android 13+)

### 6.4 Missed day / pause logic
- If the app wasn't opened on a given calendar day, do **not** silently advance `day_index` past
  it. On next open, ask: "Continue from where you left off (repeat missed day) or catch up to
  today's date?" — store the choice; log skipped days in `paused_days` for adherence stats.

## 7. Tech Stack

| Layer | Choice | Reason |
|---|---|---|
| Language | Kotlin | Native alarm reliability, first-class Android support |
| UI | Jetpack Compose | Modern, maintainable, less boilerplate than XML views |
| Local DB | Room (SQLite) | Structured relational data (users, characters, routine days) fits well; offline-first |
| Background scheduling | WorkManager + AlarmManager | Standard combo for guaranteed daily execution |
| Architecture pattern | MVVM + Repository | Standard, testable, keeps UI decoupled from data source |
| Dependency Injection | Hilt | Enterprise-standard for Android, reduces manual wiring |

## 9. Security, Performance, Scalability Notes

- **Security**: All health data (height/weight/routine progress) stored locally in Room, encrypted
  at rest via `SQLCipher` or Android's `EncryptedFile`/Jetpack Security library — no cloud sync in
  MVP, so no server-side data exposure surface.
- **Performance**: Index `DailyRoutineEntry` table on `(character_id, day_index)` for O(1) daily
  lookups; avoid loading all 1095 rows into memory — query only the current day (+/- prefetch of
  next day for the midnight rescheduling job).
- **Scalability**: Schema supports adding more characters or extending routine length without
  structural changes — just more rows. If cloud backup/multi-device sync becomes a Phase 2
  requirement, the local-first Room schema maps cleanly to a remote Postgres/Firebase mirror later.
- **Maintainability**: Routine *content* (the 5×1095 dataset) is fully separated from *app logic*
  — content updates never require a code change or app store re-review beyond a data migration.
